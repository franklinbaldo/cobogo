# Rodada — Quem São Eles?

## Foco e avaliação final

O foco foi `franklinbaldo/quem-sao-eles`. A avaliação de qualidade permanece em **23 de 24 pontos — faixa de referência**: Clareza 4/4, Explicabilidade 4/4, Autonomia 4/4, UX 4/4, UI 3/4 e Confiança 4/4.

A maior dívida continua sendo UI 3/4. Isso não quer dizer que a rota PEP esteja visualmente ruim: ela é limpa, responsiva e agora foi observada também depois da publicação. O 3/4 registra uma limitação de escopo: a prova visual profunda continua concentrada na busca PEP, enquanto a futura superfície editorial de perfis ainda não tem conteúdo populado suficiente para sustentar nota de referência visual para o projeto inteiro.

## O que estava errado ou faltando

O rodapé compartilhado usava `--gray-gradient`, `--gray` e `--gray-dark`, mas as páginas atuais não carregam o CSS legado que define essas variáveis. Portanto, fundo, cor do texto e estado do link dependiam de valores CSS ausentes no contexto real de renderização.

Havia também uma pendência antiga que já não correspondia ao código. A issue `quem-sao-eles#13` ainda dizia que o endereço do Parquet perdia a barra entre `/quem-sao-eles/` e `data/`, embora a #12 já tivesse corrigido esse mecanismo normalizando `BASE_URL`.

Por fim, a observação visual existente abria o build em um servidor local dentro do workflow. Isso provava o arquivo construído, mas não provava separadamente a página que o GitHub Pages realmente entregou ao leitor.

## O que foi feito

A PR `quem-sao-eles#25` tornou o rodapé autossuficiente: fundo branco, separação superior discreta, texto `#555` e estado de hover/foco `#111` agora são definidos localmente. A identidade jornalística preto/branco/cinza foi preservada; nenhum stylesheet antigo ou aparência genérica do Cobogó foi imposto.

Na mesma PR foi acrescentado `PEP published capture`. Depois que `Deploy to GitHub Pages` termina com sucesso em `main`, esse workflow faz checkout do commit publicado, abre `https://franklinbaldo.github.io/quem-sao-eles/pep/` diretamente em Chromium e executa o mesmo contrato funcional/visual contra a URL pública.

A #13 foi reescrita em português claro e encerrada como resolvida. A nova capacidade de observar a URL pública depois do deploy foi encaminhada ao `franklinbaldo/workspace` pela issue #41; o `ProjectProfile` não foi editado por esta rotina.

## O que ficou comprovado

Na #25, o commit atual da branch antes do merge foi `70275276b3b80a2000e1a1fe8b2b4dd88ca7eadd`. Nesse commit, `GitGuardian Security Checks`, `build` e `capture-pep` terminaram verdes. A PR estava mergeável e foi incorporada.

O commit que realmente entrou em `main` após o merge foi `4e412c8e4ae5b275dc9525dc97c9ecf066c8d384`.

A publicação `33851656399`, correspondente exatamente a esse commit, terminou verde: construção e `Deploy to GitHub Pages` concluíram com sucesso.

Em seguida, a primeira observação pós-publicação, execução `33852287508`, também terminou verde no mesmo commit. Ela fez checkout de `4e412c8e...`, confirmou que a rota pública respondia, abriu a página em Chromium, executou `Capture the page readers actually receive` e enviou o pacote `9928944933`, chamado `pep-published-evidence-4e412c8e4ae5b275dc9525dc97c9ecf066c8d384`.

Assim, há prova separada para os três estados relevantes: branch da PR, commit incorporado em `main` e URL pública depois da publicação.

Também ficou comprovado que a antiga #13 não representava uma falha presente: o código atual mantém a normalização do `BASE_URL` e as execuções posteriores da busca PEP usam o endereço correto.

## O que ainda falta

Nada falta para o problema escolhido nesta rodada. A mudança do rodapé foi incorporada, publicada e observada na URL pública.

A dívida UI 3/4 continua existindo por um motivo diferente e mais amplo: não há conteúdo editorial populado suficiente para avaliar a linguagem visual da futura superfície de perfis com a mesma profundidade da busca PEP. Não foi aberta uma issue genérica para “melhorar UI”, porque isso fabricaria trabalho sem um defeito concreto.

A issue `workspace#41` continua aberta apenas para que o repositório com autoridade sobre `ProjectProfile` registre a nova capacidade comprovada.

## Opinião Cobogó aplicada

Aplica-se `visual-evidence-as-quality-gate`, atualmente `stable`. Em linguagem comum, isso significa que a recomendação já funcionou de forma convergente em pelo menos dois projetos reais: uma mudança visual não é considerada concluída só porque o CSS parece certo ou o build passou; ela precisa ser observada no navegador no estado que queremos afirmar como entregue.

O Quem São Eles? acrescenta um aprendizado útil à implementação dessa opinião: em projetos publicados, observar o build e observar a URL depois do deploy são provas diferentes. A #25 transforma essa distinção em comportamento automático do repositório.

A próxima rodada **não deve voltar imediatamente ao Quem São Eles?**. O problema escolhido foi corrigido, incorporado, publicado e observado novamente no endereço público. Só faz sentido retornar se surgir um fato novo capaz de mudar a avaliação — por exemplo, regressão, nova superfície editorial populada ou um defeito concreto revelado por uma futura observação.
