# Rodada — Perquire: transformar teste de template em evidência real de navegador

## Situação percebida antes da mudança

O Perquire está ativo e o `ProjectProfile` do workspace o classifica como prioridade alta. O registro do Cobogó ainda descreve uma interface FastAPI/Jinja local, com teste automatizado que renderiza templates, mas sem captura controlada em navegador real. Isso significa que sabemos que o HTML consegue ser produzido, mas ainda não temos pixels reproduzíveis para julgar responsividade, hierarquia visual e comportamento da página em larguras diferentes.

Nas três perguntas de entrada, o estado atual é: **Clareza/D1** aparentemente forte pela própria página e documentação, mas ainda sem nota porque falta avaliação completa; **Explicabilidade/D2** tem evidência de código/documentação sobre investigação, persistência e exportação; **Autonomia/D3** tem caminhos de exportação JSON/CSV/texto. Nenhuma dessas três observações autoriza pontuar UI/UX sem navegador.

A dimensão escolhida nesta rodada é **UI/UX verificável**. O problema concreto não é afirmar que a aparência está ruim: é que o projeto ainda não produz a evidência necessária para saber, de forma reproduzível, se a interface real continua legível e utilizável em desktop e tela estreita.

## Problema escolhido e critério congelado

O problema escolhido foi: **o workflow `Web surface` prova apenas renderização Jinja; ele não abre a aplicação em um navegador real nem preserva imagens que permitam revisar a superfície como o usuário a vê**.

Antes de alterar o Perquire, fica congelado o seguinte critério de conclusão: uma execução sem credenciais deve iniciar a aplicação FastAPI real, abrir `/` com Chromium, produzir pelo mesmo método uma imagem desktop com largura de pelo menos 1024 px e uma imagem estreita com largura de no máximo 480 px, nomear o arquivo de evidência com o commit realmente testado e publicar essas imagens como arquivo do workflow tanto em PR quanto em `main`. A captura não deve chamar provedor externo nem exigir segredo.

A recomendação Cobogó aplicável é `visual-evidence-as-quality-gate`. Ela está **stable**, isto é, já funcionou de forma convergente em pelo menos dois projetos reais. Aqui ela não dita aparência: apenas exige que uma decisão visual seja apoiada por pixels reproduzíveis do código real.

## O que estava errado ou faltando

Faltava uma ponte entre o teste de template e a avaliação visual. O workflow atual instala a fronteira web e executa `tests/test_web_surface.py`, mas não inicia o servidor, não abre Chromium e não guarda screenshot. Assim, uma mudança de CSS ou de responsividade pode passar pelo teste sem que a rotina tenha uma imagem real para revisar.

## O que foi feito

Este relatório foi criado antes de qualquer modificação no Perquire, registrando o problema e o critério acima. A implementação no consumer ainda não começou neste ponto do relatório.

## O que ficou comprovado

No `main` atual do Perquire, commit `044a6998844dc0852d479522f33f525381a15bc7`, existe o workflow `.github/workflows/web-surface.yml`; ele sincroniza o extra `web` e executa somente o teste de template. A busca no repositório não encontrou Playwright, screenshot ou outro mecanismo de captura de navegador. O `ProjectProfile` do workspace mantém o projeto ativo e de alta prioridade, portanto ele continua elegível para esta rodada.

## O que ainda falta

Ainda é necessário implementar a captura controlada no Perquire, abrir a PR, verificar os checks no commit atual da branch, fazer merge apenas se os checks obrigatórios estiverem verdes e a PR estiver mergeável, confirmar que o workflow roda também no commit que entrar em `main` e então abrir as imagens produzidas. Só depois disso haverá base para criar a primeira avaliação completa de qualidade da interface.

## Por que a próxima rodada deve ou não voltar

Se esta rodada conseguir implementar, mergear e obter as imagens de `main`, o Perquire não deve ser repetido automaticamente: a própria avaliação visual dirá se existe um problema concreto que merece nova intervenção. Se a captura falhar por um motivo objetivo que não possa ser corrigido dentro do orçamento, a próxima rodada só deve voltar quando houver um fato novo que permita avançar; caso contrário, deve rotacionar para outro projeto ativo.
