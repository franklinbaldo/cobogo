# Rodada — Cobogó: depreciação precisa ser decisão, não acúmulo automático

## O que estava errado ou faltando

Baliza continua com a menor avaliação de qualidade, 20 de 24 pontos, mas a correção visual já está em `main` e a publicação permanece presa ao mesmo impedimento operacional, sem fato novo. Leizilla também não deve ser repetido enquanto a observação oficial continuar incapaz de abrir uma norma. Sisprev permanece em 22 de 24 pontos sem defeito novo concretamente demonstrado.

No próprio Cobogó existe trabalho executável e já aceito pela RFC 0003: a issue #485 registra que a política de compatibilidade ainda está espalhada em frases de princípio. Sem um procedimento curto, uma API antiga pode ficar indefinidamente como wrapper, alias ou componente histórico apenas por receio genérico de quebrar projetos.

A avaliação vigente do Cobogó permanece 24 de 24 pontos: Clareza 4/4, Explicabilidade 4/4, Autonomia 4/4, UX 4/4, UI 4/4 e Confiança 4/4. O problema desta rodada é uma dívida operacional de evolução do design system e não justifica rebaixar uma dimensão pública inteira.

## Critério verificável fixado antes da mudança

1. A documentação deve permitir classificar uma mudança de API como compatível ou incompatível em uma frase curta.
2. Toda depreciação deve registrar motivo, substituto quando houver e uma condição explícita para remoção; não pode significar “manter para sempre”.
3. Uma versão nova pode remover uma API antiga sem exigir que todos os projetos tenham migrado; quem não puder migrar pode permanecer numa versão anterior.
4. Wrapper de compatibilidade só permanece enquanto houver utilidade concreta registrada; ausência de consumidor conhecido favorece remoção na próxima mudança incompatível adequada.
5. Quando houver projeto conhecido usando a API, a orientação de migração deve dizer o que trocar, sem criar aprovação central para a mudança local do projeto.
6. A política deve apontar como fonte para PRs de consolidação e ficar ligada à RFC 0003, sem duplicar toda a RFC.
7. Como esta é uma mudança documental/operacional sem alteração visual material do site, não haverá print antes/depois inventado; os verificadores de documentação e build continuam obrigatórios no commit atual da PR.

A tese aplicada é a própria decisão da RFC 0003: compatibilidade é útil, mas não é superior à simplicidade. Em linguagem comum, o Cobogó deve conseguir corrigir abstrações ruins em versões novas, enquanto projetos que não possam acompanhar imediatamente permanecem numa versão anterior.

## O que foi feito

Pré-registro concluído antes da alteração substantiva. A implementação ainda não foi aplicada neste ponto do relatório.

## O que ficou comprovado

Até aqui, ficou comprovado que #485 continua aberta e que a RFC 0003 já aceita mudanças incompatíveis quando elas reduzem duplicação ou melhoram materialmente a abstração, sem exigir migração imediata dos projetos.

## O que ainda falta

Escrever a política operacional curta, ligá-la à documentação de desenvolvimento, abrir uma única PR substantiva, validar o commit atual da branch e incorporar somente se os verificadores pertinentes estiverem verdes.

## Por que a próxima rodada deve ou não voltar

Este ponto só será decidido depois da execução. Se a política entrar e ficar verificável, a próxima rodada deve avançar para outra frente da RFC 0003 ou para outro projeto; se houver falha objetiva nos verificadores, o retorno dependerá da causa registrada.
